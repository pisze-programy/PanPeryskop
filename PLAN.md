# PanPeryskop — Implementation Plan (MVP, Poznań)

> **Product:** PanPeryskop — "see what's happening in your city". Periscope-style, geo-anchored social media for Poland. MVP scoped to Poznań, expandable to other cities.
> **App name (store, final TBD):** PanPeryskop — zobacz co się dzieje w mieście
> **Target platform:** iOS (Swift, SwiftUI), min **iOS 18**
> **App Store release:** out of scope for MVP (no paid Apple Developer account yet — dev account only).

---

## 1. Confirmed decisions

| Area | Decision |
|---|---|
| Backend | Cloudflare Workers (TypeScript, hono router) + D1 (SQLite) + R2 (media storage) |
| Map engine | **MapKit (native Apple)** — no SPM dependency, iOS 18+ `Map` SwiftUI view + overlays |
| Tile hosting | N/A — MapKit uses Apple Maps tiles by default |
| Min iOS | **iOS 18** (middle ground between reach and modern SwiftUI APIs) |
| Auth | **Fake auth**: `device_id` → `session_token` generated by backend. Real OAuth (Apple + Google) planned in sections 8e–8f |
| Video pager | **SwiftUI-LazyPager** (MIT) — vertical paging, lazy load, overscroll |
| Popularity | `score = views + 3·likes + 5·shares` + slight time decay. Weights configurable in backend |
| Watched logic | Reel watched (video end / photo 60s timeout / explicit exit) → hidden for that user forever + counts as exactly 1 unique view |
| Media capture | Camera **and** gallery allowed; **auto-save recordings to Photos** as backup |
| Moderation | CLI/SSH on backend (wrangler) with secret token; admin approves/rejects pending posts |
| Map styles | Single simple, readable OSM style for MVP; more styles later |
| Profile | Minimal — device identity only, **no "my posts"** |
| UI language | Polish |
| Live streaming | Out of scope for MVP (photo/video/text only) |
| Monetization | None in MVP; app fully free |
| Content TTL | 24h visibility (`expires_at`), **not deleted** from backend |

**Working principle:** prefer battle-tested, popular, MIT-licensed GitHub libraries over writing custom code for UI, map, paging, aggregation, and popularity logic. Verify each library: license, stars, last-commit date, maintenance status.

## 3. Data model (D1 / SQLite)

```sql
CREATE TABLE users (
  id            TEXT PRIMARY KEY,            -- nanoid
  device_id     TEXT NOT NULL UNIQUE,
  session_token TEXT NOT NULL,
  role          TEXT NOT NULL DEFAULT 'user', -- 'user' | 'admin'
  created_at    INTEGER NOT NULL             -- unix ms
);

CREATE TABLE posts (
  id            TEXT PRIMARY KEY,            -- nanoid
  user_id       TEXT NOT NULL REFERENCES users(id),
  type          TEXT NOT NULL,               -- 'photo' | 'video' | 'text'
  lat           REAL NOT NULL,
  lng           REAL NOT NULL,
  description   TEXT DEFAULT '',
  status        TEXT NOT NULL DEFAULT 'pending', -- 'pending' | 'approved' | 'rejected'
  media_key     TEXT,                        -- R2 object key (NULL for text posts)
  thumb_key     TEXT,                        -- R2 thumbnail key (optional, for video)
  created_at    INTEGER NOT NULL,
  expires_at    INTEGER NOT NULL,            -- created_at + 24h
  likes_count   INTEGER NOT NULL DEFAULT 0,
  views_count   INTEGER NOT NULL DEFAULT 0,
  shares_count  INTEGER NOT NULL DEFAULT 0,
  grid_cell_id  TEXT                         -- derived from lat/lng
);

CREATE TABLE views (
  user_id   TEXT NOT NULL REFERENCES users(id),
  post_id   TEXT NOT NULL REFERENCES posts(id),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, post_id)             -- exactly 1 unique view per user
);

CREATE TABLE likes (
  user_id   TEXT NOT NULL REFERENCES users(id),
  post_id   TEXT NOT NULL REFERENCES posts(id),
  created_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, post_id)
);

CREATE TABLE grid_cells (
  id    TEXT PRIMARY KEY,                    -- "lat_ix:lng_ix" for the grid
  lat   REAL NOT NULL,                       -- cell center
  lng   REAL NOT NULL,
  heat  INTEGER NOT NULL DEFAULT 0           -- live (approved, unexpired) post count
);
```

### Notes
- **Grid:** divide the viewport bounding box into fixed cells (~250–500 m at Poznań zoom). `heat` = number of `approved` posts where `expires_at > now()` whose coordinate falls in the cell. Cell id derived deterministically from coordinates (e.g. floor division by cell size).
- **TTL:** `expires_at = created_at + 24h`. All public queries filter `expires_at > now()`. Posts are **never deleted**; consider R2 lifecycle → Coldline later to cut costs (decision deferred).
- **Grid heat** can be computed on read (aggregate query) for MVP rather than maintaining `grid_cells` eagerly — simpler, fine at Poznań scale.

## 4. Backend API (Cloudflare Worker)

```
POST /auth/device            { "device_id": "..." } → { "session_token": "...", "user_id": "...", "role": "user" }
                             Upserts user, returns (re)generated token.

GET  /stories?bbox=SW_lat,SW_lng,NE_lat,NE_lng
                             → { stories: [Story] } approved + unexpired + NOT viewed by
                               caller, ordered by popularity score. Story = post + author
                               name + media URL + counts + watched flag.
POST /posts                  multipart/form-data: file (photo/video) OR text-only,
                             fields: type, lat, lng, description.
                             Requires auth. Uploads media → R2 (key = post id),
                             inserts post with status 'pending'. Returns post.
GET  /posts/:id              → post detail (only approved & unexpired).
POST /posts/:id/like         toggle like (auth). Returns new likes_count + liked bool.
POST /posts/:id/share        increments shares_count (auth).
POST /posts/:id/watched      auth; if no row in `views` → insert + views_count++. 
                             Marks as watched (drives hiding).
GET  /heatmap?bbox=          → [{ grid_cell_id, lat, lng, heat }] for active approved posts.

-- Admin (protected by ADMIN_SECRET header/token, used by CLI) --
GET  /admin/queue            → pending posts with media signed URLs + author info.
POST /admin/posts/:id/approve
POST /admin/posts/:id/reject
```

### Popularity score (server-side SQL)
```
score = views_count + 3*likes_count + 5*shares_count
       * pow(decay, age_hours)          -- e.g. decay=0.99
```
Weights (`WV=1, WL=3, WS=5, DECAY=0.99`) configurable via env vars. Server returns pre-sorted list.

### Auth model (fake)
- Client generates a persistent `device_id` (UUID stored in Keychain) on first launch.
- `POST /auth/device` exchanges it for a `session_token`. Client sends `Authorization: Bearer <token>`.
- `users.role` default `user`; promote an account to `admin` via CLI/wrangler for moderation testing.

## 5. iOS app — screens (SwiftUI, Polish UI)

### 5.1 Onboarding / Login (first screen)
- Simple full-screen view: app name, short tagline ("Zobacz co się dzieje w mieście"), CTA button **"Wejdź do aplikacji"**.
- On tap: ensure `device_id` exists (Keychain) → `POST /auth/device` → store token → navigate to main map.
- No real auth, no forms. (Real OAuth via Apple + Google is planned — see sections 8e–8f.)

### 5.2 Map (main screen)
- MapLibre map centered on **Poznań: 52.4064, 16.9252**, fixed default zoom (~city level).
- Overlay: **heatmap grid** — semi-transparent cell fills; intensity/color from `heat` (e.g. transparent → yellow → orange → red at threshold). Fetch via `GET /heatmap?bbox=` debounced.
- **Clustering:** pins for posts; cluster when zoomed out, expand to individual pins as zoom increases (city → street level). Use MapLibre clustering (or SwiftUI-LazyPager-scale pattern: prefer existing lib if available).
- Interactions:
  - Tap on grid cell / cluster / pin → bottom list of posts in that region + post detail ("wydarzenie" e.g. forest-fire report shows detail view).
  - Region change (pan/zoom) → **debounce ~500 ms** → refetch stories bar + heatmap (mirror of JS input-timeout pattern; prevents jitter).
- Zoom-out to max city level → aggregated view, no more unread stories → nothing further happens.

### 5.3 Stories bar (overlaid on top of map, NOT a tab)
- Horizontal `ScrollView` of **16:9 rounded thumbnails** pinned above the map.
- Data: `GET /stories?bbox=`. Sorted by popularity (server). Only **unwatched** posts.
- Refreshes with debounce on region change.
- Tap a thumbnail → open fullscreen viewer at that index.
- If no unwatched stories in region → empty/absent bar.

### 5.4 Fullscreen story viewer (TikTok-style)
- **SwiftUI-LazyPager** (MIT) with `direction: .vertical`, full-screen, ignores safe areas.
- Content:
  - **Video:** plays on appear; at end → auto-advance to next reel (**autoswipe**) and mark watched.
  - **Photo:** shown for **60 seconds** → autoswipe → mark watched.
- Action rail (right side, bottom area, Instagram-style): like (heart) with count, share, views count — icon + text stacked vertically.
- Progress: thin top progress bar / simple indicator.
- **Watched semantics:** video end / photo timeout / explicit exit → `POST /posts/:id/watched` + remove from local unwatched list + hidden on next refetch. A watched reel cannot be reopened from the bar.
- **Overscroll end** (last reel in region): exit viewer → trigger map refresh (refetch stories + heatmap) → user can re-enter bar and loop again.
- Exit also on swipe-down dismiss if LazyPager supports it (vertical primary).

### 5.5 Add content (+)
- Entry from a prominent FAB or a "Dodaj" button on the map.
- Options: **photo**, **video**, or **text post**.
  - Camera (AVFoundation / SwiftUI `Camera` on iOS 17+, fallback to `UIImagePickerController`) **and** gallery picker (`PhotosPicker`).
  - **Auto-save captured recording/photo to the Photos library** as a backup copy (request `NSPhotoLibraryAddUsageDescription`).
- Fields: capture/select media OR text, optional description, **location pin** (current location default, draggable/auto-pinned).
- Submit → `POST /posts` (multipart). Status shown: "Oczekuje na weryfikację".
- Requires auth (fake token) — user is always "logged in" via device session.

### 5.6 Profile (minimal)
- Device identity display (device id short form / placeholder name).
- No "my posts" list. Logout option (clears token/device_id → returns to onboarding).

## 8a. Location — iteration 1 (implemented)

**Scope:** native blue-dot user marker on the Map tab with live updates; **no camera follow** (marker updates without affecting the current map view), no heading UI, no distance-to-stories UI, no trail yet.

- **MapKit API (iOS 17+ content-builder Map):** no `.showsUserLocation` / `.userTrackingMode` modifiers on the modern API. Use `UserAnnotation()` in the Map content builder — renders the blue dot and updates live, independent of the camera. Camera stays a static `.region(Poznań)`; the user pans freely, the marker just moves (and leaves the viewport when you walk away).
- **UI:** no follow control, no recenter control — the user pans freely, the marker just moves (and leaves the viewport when you walk away). (A former "Wróć do centrum" pill existed in this iteration but was later removed — see 8g.)
- **Permission:** reuses the existing `WhenInUse` prompt (already granted during Add Content). Updated `NSLocationWhenInUseUsageDescription` text in `project.yml`; regenerate with `xcodegen generate --spec ios/project.yml`.
- **Battery (foreground-only, this iteration):** no custom `CLLocationManager` — MapKit powers the dot itself; location active only while the map is visible. No follow = no extra camera work.
- **v2 (deferred):** heading captured in Add Content data (`startUpdatingHeading` only during capture, then stop), trail overlay (`MapPolyline` in user color), nearest-stories distance. If a custom `CLLocationManager` becomes necessary: `desiredAccuracy = .HundredMeters` (+ `Reduced` fallback), `distanceFilter` 10–50 m, `pausesLocationUpdatesAutomatically = true`, `activityType = .other`, start/stop bound to the Map tab lifecycle, never `kCLLocationAccuracyBestForNavigation`.

## 8c. Map pins / seen model (implemented)

- **Heatmap boundaries removed** (iOS + fetch; `Models/GridCell.swift` deleted, backend `/stories/heatmap` stays unused).
- **Horizontal 9:16 stories bar removed** — entry to stories is only via map pins/groups (`StoriesBarView.swift` deleted; `StoryAvatar`/`StoryDateFormatter` moved into `StoryFullScreenView.swift`).
- **Group pins:** round pin = uniform accent color + bold count `N` (no thumbnail, no lock), wrapped in a TTL ring animated for the **oldest member** (TimelineView). `Annotation` uses no title label (fixes duplicate count).
- **Group tap → viewer:** group stories (unseen) by popularity first, then remaining region stories by popularity. **Single pin tap:** clicked story first, then remaining region stories. `ContentView` drives the viewer from `@State storyPosts`.
- **Seen model (replaces "watched → hidden"):** a story is marked seen when its media fully loads in the preview AND the user advances or closes the viewer (`markSeen` in `StoryFullScreenView`; pending/my posts never marked). Seen pins stay on the map but **dimmed (`opacity` 0.4) + red `eye.slash.fill` badge, non-clickable**. Seen posts are **excluded from groups** (not counted, not in group viewer). Requires backend `/stories` to return seen posts with `watched: true` (LEFT JOIN `views`).

## 8d. Media compression on upload (implemented)

- **Photos:** on-device — downscale to max 1080px + JPEG q0.8 (`MediaCompressor.optimizePhoto`) → ~150–400 KB (was full-res).
- **Videos:** on-device re-encode right after capture, **in the background (invisible)** — `T2Je/FYVideoCompressor` (MIT, ~73★, SPM) via `MediaCompressor.compressVideo` (≤720p, ~4 Mbps, 30 fps, audio 96k → ~30 MB for 60 s). `DescriptionStepView` starts compression on appear; `publish()` awaits it (falls back to original file on failure). Recording limit stays 60 s.
- **Thumbnails (photo + video):** uploaded with the post (multipart `thumb`, 320px JPEG), stored as `posts/{id}/thumb.jpg`, `thumb_key` persisted + returned; `Post.resolvedThumbURL` falls back to `thumb_key` so pending pins show a real thumbnail immediately.
- **`UIImage.resized(to:)` fix:** renders at `format.scale = 1` (pixel-based) — previously the renderer used the device 3× scale so "2048" produced full-res output. Avatar now 128px q0.7.
- **HTTP Range (inline `app.all('/media/*')` in `index.ts`):** R2 range reads + `206 Partial Content`/`Content-Range`/`Accept-Ranges` — required by AVPlayer for remote MP4 streaming (files in R2 were always valid; without Range the app could not play them).
- **Backend guard:** `POST /posts` rejects files > 100 MB (413). No backend transcoding (Workers can't run ffmpeg).
- **Backfill (done via `admin/scripts/backfill-media.mjs`):** existing photos re-compressed to 1080px, thumbnails generated for all posts (photo: `sips`; video: `ffmpeg` frame), `thumb_key` updated in D1, corrupt 73-byte photo removed. Requires wrangler with the `dev-4cb` account (the deployed Worker's account — local login differed).

## 8e. Apple OAuth — implementation plan

> **Status:** planned, before implementation. Decisions agreed 2026-08-06.

### Identity model (agreed)

- **`device_id` = account identity** (UNIQUE, permanent, the key for bans). Two devices
  signed in with the same Apple ID → **two independent users** (no linking by `apple_id`).
- **Apple = "prestige"**: the only way into the app, identity confirmation, but not the
  account key. `users.apple_id` stays **nullable and non-unique** (columns already in place
  since migration 0005), `auth_provider='apple'`.
- **Permanent ban by `device_id`** — blocks both `/auth/device` and `/auth/apple` (403).
  Creating a new account on a banned device — even with a different Apple ID — is impossible,
  because the account is always created against the same `device_id`.
- **Acknowledged trade-off:** the ban does not catch a full iOS reset (new `device_id` = new
  account). Unavoidable with the per-device model, without binding to the Apple ID.
- **Hard blocker:** dev account only (no $99/year) → the native `SignInWithAppleButton` will
  not return a real `identityToken` until the App ID has the capability. Requires a **dev
  mode with simulation** so the whole flow is testable right now.

### 1. Backend (Cloudflare Workers + D1)

**Migration `0007_ban.sql`:**
```sql
CREATE TABLE IF NOT EXISTS banned_devices (
  device_id  TEXT PRIMARY KEY,
  reason     TEXT,
  banned_at  INTEGER NOT NULL
);
```

**`backend/src/auth.ts`:**
- Shared helper `isBanned(db, device_id)` — `SELECT 1 FROM banned_devices WHERE device_id = ?`.
- `POST /auth/device` → ban check first → `403 {error: 'banned'}`.
- New `POST /auth/apple`:
  1. Body: `{ identity_token, device_id }` (`device_id` validated as in `/device`).
  2. Ban check → 403.
  3. JWT verification: fetch `https://appleid.apple.com/auth/keys`, pick the key by `kid`,
     RS256 verify via `crypto.subtle` (WebCrypto — zero new dependencies), check
     `iss === "https://appleid.apple.com"`, `aud === "com.panperyskop.PanPeryskop"`, `exp`.
     `sub` = `apple_id`.
  4. `SELECT ... FROM users WHERE device_id = ?` → exists: `UPDATE ... SET apple_id = ?,
     session_token = ?` → return the user (as in `/device`).
  5. Does not exist: `INSERT` a new user (`auth_provider='apple'`, `apple_id=sub`,
     `session_token`, username from `full_name` or `defaultUsername()`) → `201 is_new: true`.
- **Dev mode (no paid account):** when `ENVIRONMENT !== 'production'`, the endpoint accepts
  the `{ device_id, apple_user_id, full_name }` variant without JWT verification
  (simulation). In production verification is always required.

**`backend/src/users.ts`:** `GET /users/me` additionally returns `auth_provider` + a
`has_apple` flag (for the profile UI).

**Admin:** `admin/src/cli.js` + `/admin/ban` endpoint (POST, `ADMIN_SECRET`):
`ban <device_id> [reason]` / `unban <device_id>`. The `banned_devices` table is the source of truth.

### 2. iOS (SwiftUI, XcodeGen)

- **`ios/PanPeryskop/SignInWithApple.entitlements`** (`com.apple.developer.applesignin` =
  `[Default]`) + `entitlements:` entry in `project.yml` → `xcodegen generate`.
- **New file `Services/AppleSignIn.swift`:** `UIViewRepresentable` wrapper around
  `SignInWithAppleButton` (drives `ASAuthorizationController`, the delegate returns
  `identityToken`/`fullName`/`sub`). Under `#if DEBUG` the button generates a fake
  `identityToken` (random `apple_user_id`) instead of the native sheet → same backend endpoint.
- **`AuthManager`:** keychain unchanged (`device_id` stays). Add `loginWithApple()` →
  `POST /auth/apple` (via `APIClient`), store `session_token`/`user_id`/`username` as in
  `login()`; `Error 403` → dedicated "Device banned" message. Store `apple_user_id` in the
  Keychain (for future `getCredentialState`).
- **`APIClient`:** `authHeaders()` unchanged (same `session_token`).
- **`OnboardingView`:** "Enter the app" replaced by the "Sign in with Apple" button (official
  `SignInWithAppleButton`, PL localization from the system). In DEBUG a small fallback link
  "Enter without logging in" below it (dev-only, plain `/auth/device`).
- **`ProfileView`:** shows "Signed in with Apple" under the name when `has_apple`. Logout
  unchanged.

### 3. Testing (two devices, same Apple ID)

Same Apple ID on two iPhones → two separate `device_id`s → two users. A ban on one device
does not affect the other.

1. `cd backend && npm run db:migrate` (0007) + `npx wrangler dev`.
2. curl: `POST /auth/apple` (dev mode) → creates/logs in; `POST /auth/apple` with a banned

3. iOS: `xcodegen generate` → build → onboarding via Apple (simulation in DEBUG), profile

## 8f. Google OAuth alongside Apple — implementation plan

> **Status:** planned, before implementation. Decisions agreed 2026-08-06. Google is added
> **alongside** Apple (plan 8e) — it does not replace it. Identity model, ban and session
> are identical to 8e (`device_id` = identity, `google_id` nullable and non-unique, ban by
> `device_id`).
>
> **Rationale:** Apple requires $99/year (capability blocked); Google works today for free
> (OAuth client in the Google Cloud Console). Adding Google alongside Apple satisfies App
> Store Rule 4.8 (third-party login also requires Sign in with Apple) and provides a working
> login right now, without changing the Apple plan.

### Backend

- **`backend/src/oauth.ts`** (new): shared `verifyIdToken({ jwksUrl, issuer, aud, token })`
  — fetch JWKS, pick the key by `kid`, RS256 verify via `crypto.subtle` (WebCrypto, zero new
  dependencies), check `iss`/`aud`/`exp`. Used by `/auth/apple` and `/auth/google`.
- **Migration `0008_google.sql`:** `ALTER TABLE users ADD COLUMN google_id TEXT;` (the ban
  stays in `0007_ban.sql`).
- **`POST /auth/google`** in `auth.ts` — mirror of `/auth/apple`:
  1. Body: `{ identity_token, device_id }` (validated as in `/device`), ban check → 403.
  2. Verification: JWKS `https://www.googleapis.com/oauth2/v3/certs`, `iss` ∈
     `{accounts.google.com, https://accounts.google.com}`, `aud` = `GOOGLE_CLIENT_ID` (env
     var), `sub` → `google_id`.
  3. `SELECT ... WHERE device_id = ?` → exists: `UPDATE google_id + session_token` → return
     the user (as in `/device`).
  4. Does not exist: `INSERT` a new user (`auth_provider='google'`, `google_id=sub`,
     `session_token`, username from `given_name`/`name` or `defaultUsername()`) → `201 is_new: true`.
- **`wrangler.toml` vars:** `GOOGLE_CLIENT_ID`, `APPLE_CLIENT_ID` (= bundle ID).
